You will remove the environment in dependency order: stop active workloads, then
let Terraform remove the Flex host, Kubernetes resources, and Azure resources.
The final checks confirm that both Azure resource groups and Terraform state are
empty.

## What You Will Do

One command performs the cleanup, but the order still matters. You will stop
active jobs first, remove the deployed resources, and check the result. The same
`.env` file can be used later to create a new environment.

## Teardown order

Destroying resources out of order causes Azure API conflicts (for example, deleting
the VNet before the Flex host is unjoined, or destroying the AKS cluster before the
Anyscale cloud is de-registered). The correct order is:

1. Drain and stop active Anyscale Jobs
2. Confirm that no active [Anyscale Services](https://docs.anyscale.com/services) or [Workspaces](https://docs.anyscale.com/workspaces) use the lab cloud
3. Terminate the Anyscale system cluster and archive the lab compute configs
4. Let Terraform delete the Gateway, operator extension, and Azure Anyscale cloud resources in dependency order
5. Let Terraform remove the Flex host permission and then the Flex host
6. Let Terraform destroy AKS, identities, storage, networking, and the resource group
7. Confirm that both resource groups and Terraform state are empty

## Step 1: Stop active Anyscale jobs

Check the exact lab cloud for jobs created by any user. The full ARM-style cloud
name prevents the CLI from falling back to an unrelated organization default:

```bash
source .env
export ANYSCALE_HOST="https://console.azure.anyscale.com"
RG="rg-${TF_VAR_project}-${TF_VAR_environment}-${TF_VAR_region_short}"
CLOUD="/subscriptions/${TF_VAR_azure_subscription_id}/resourcegroups/${RG}/providers/anyscale.platform/clouds/${TF_VAR_project}-${TF_VAR_environment}-${TF_VAR_region_short}"

.venv/bin/anyscale job list \
  --v2 \
  --cloud "$CLOUD" \
  --include-all-users \
  --state STARTING \
  --state RUNNING \
  --json \
  --no-interactive
```

Expected empty result:

```json
[]
```

An empty array means no Anyscale Job is starting or running on this cloud.

If the array contains a job, terminate it by immutable ID rather than by name:

```bash
JOB_ID="<job-id>"
.venv/bin/anyscale job terminate --id "$JOB_ID"
```

Example output:

```text
Marked job '<job-name>' for termination
```

## Step 2: Delete the lab resources

```bash
./scripts/anyscale-aks.sh destroy
```

Before Terraform changes Azure resources, the command resolves the exact
Anyscale cloud, lists `STARTING` and `RUNNING` Jobs for all users, terminates them
by ID, and waits up to five minutes for the active list to become empty. It stops
without deleting Azure resources if the cloud cannot be queried or the Jobs do
not terminate. That check prevents the AKS cluster from disappearing while
Anyscale still considers a lab Job active.

The lab creates Jobs, but it does not create Anyscale Services or Workspaces.
The command lists both resource types against the same full cloud name and stops
if any active entry exists. Terminate that resource explicitly, then rerun the
destroy command. This guard avoids deleting shared infrastructure that another
user still needs.

After all workload checks pass, the command runs
`anyscale cloud terminate-system-cluster --id <cloud-id> --wait`. Terraform does
not start deleting Azure resources until Anyscale confirms that the system
cluster has terminated. The lab-owned `cpu-home` and `gpu-dual-home` compute
configs are then archived by ID. If the Azure-hosted API does not support
archiving, you get a warning and cleanup continues, so leftover configuration
records do not block removal of billable Azure resources.

Only after those checks does the command run `terraform destroy -auto-approve`
with the same variable profile used to deploy. Terraform releases the Gateway
public IP, removes the AKS operator extension and Azure Anyscale cloud resources,
then deletes the remaining AKS, Flex host, identity, storage, registry,
observability, and networking resources. If Azure rejects a deletion, Terraform
stops and preserves the remaining objects in state for the next run.

Expected duration: **10-20 minutes** (AKS cluster deletion is typically the longest step).

Example completion lines:

```text
info: no active Anyscale Jobs remain on cld_<cloud-id>
info: no active Anyscale Services or Workspaces remain on cld_<cloud-id>
info: Anyscale system cluster is terminated for cld_<cloud-id>
azurerm_kubernetes_cluster_extension.anyscale_operator[0]: Destruction complete
azapi_resource.anyscale_cloud_resource[0]: Destruction complete
azapi_resource.anyscale_cloud[0]: Destruction complete
azurerm_kubernetes_cluster.aks: Destruction complete
azurerm_resource_group.this: Destruction complete
Destroy complete!
```

:::warning Transient Azure errors during destroy
Azure occasionally returns transient control-plane errors such as `AnotherOperationInProgress`.
Wait for the active Azure operation to finish or return an error, then rerun the
same destroy command. It is safe to retry and will continue from where it stopped.
Use `./scripts/validate-lab.sh teardown` in Step 3 instead of manually deleting
related resources.
:::

**Anyscale RP deletion errors:**

Terraform owns `Anyscale.Platform/clouds` and `cloudResources/default` directly.
If the resource provider rejects either deletion, Terraform reports the provider
error and leaves the AKS dependencies in state. Do not delete the resource group,
AKS cluster, or managed identity around that failure. Preserve the state and ask
your Anyscale/Azure provider contact to reconcile the blocked cloud resource.

:::info Stale Anyscale console entries
This lab owns its Anyscale cloud through the `Anyscale.Platform` Azure resource,
so teardown uses the Azure RP path rather than `anyscale cloud delete`. If the
Azure resource group and `Anyscale.Platform/clouds` ARM resource are gone but the
Anyscale console still lists an old cloud with no resources, treat it as a stale
control-plane registration and ask your Anyscale/Azure provider contact to remove
it. Do not use `anyscale cloud delete --force` or keep retrying Azure Portal
deletes for a cloud that no longer exists in Azure ARM.
:::

## Step 3: Confirm Azure resources and Terraform state are empty

After destroy completes:

```bash
# Confirm that Azure resources and Terraform state are empty
./scripts/validate-lab.sh teardown
```

Expected output:

```text
PASS M7-01 resource group deleted
PASS M7-02 AKS managed resource group deleted
PASS M7-03 terraform state empty
```

If you want to inspect the underlying values directly, derive them from `.env`:
an empty `terraform state list` is a success condition, so it prints no resource
lines after the two `false` values.

```bash
source .env
RG="rg-${TF_VAR_project}-${TF_VAR_environment}-${TF_VAR_region_short}"
CLUSTER="aks-${TF_VAR_project}-${TF_VAR_environment}-${TF_VAR_region_short}"
AKS_MANAGED_RG="MC_${RG}_${CLUSTER}_${TF_VAR_azure_location}"
az group exists -n "$RG"
az group exists -n "$AKS_MANAGED_RG"
terraform -chdir=infra/terraform state list
```

Expected output:

```text
false
false
```

`terraform state list` should print no resources.

## Step 4: Confirm teardown is repeatable

Run destroy a second time to confirm it is a no-op:

```bash
./scripts/anyscale-aks.sh destroy
```

Expected output ends with:

```text
No changes. No objects need to be destroyed.
```

## Confirm cleanup is complete

Save the final cleanup results before discarding the environment:

```bash
(
set -euo pipefail
mkdir -p .cache/teardown
./scripts/validate-lab.sh teardown | tee .cache/teardown/checks.txt
source .env
RG="rg-${TF_VAR_project}-${TF_VAR_environment}-${TF_VAR_region_short}"
CLUSTER="aks-${TF_VAR_project}-${TF_VAR_environment}-${TF_VAR_region_short}"
AKS_MANAGED_RG="MC_${RG}_${CLUSTER}_${TF_VAR_azure_location}"
az group exists -n "$RG" > .cache/teardown/rg-exists.txt
az group exists -n "$AKS_MANAGED_RG" > .cache/teardown/aks-managed-rg-exists.txt
if ! TF_STATE="$(terraform -chdir=infra/terraform state list)"; then
  echo "FAIL: unable to read Terraform state" >&2
  exit 1
fi
printf '%s\n' "${TF_STATE:-empty}" > .cache/teardown/tf-state.txt
echo "teardown complete $(date -u +%Y-%m-%dT%H:%M:%SZ)" > .cache/teardown/summary.txt
cat .cache/teardown/rg-exists.txt \
  .cache/teardown/aks-managed-rg-exists.txt \
  .cache/teardown/tf-state.txt
)
```

Expected output:

```text
PASS M7-01 resource group deleted
PASS M7-02 AKS managed resource group deleted
PASS M7-03 terraform state empty
false
false
empty
```

The `PASS` results and final three values confirm that the primary and AKS managed
resource groups are gone and Terraform has no resources in state.

## Create the environment again

The retained `.env` file contains the settings for a replay. The apply command
regenerates `terraform.auto.tfvars.json` from those settings, and Step 3 already
showed that Terraform state contains no managed resources. You can therefore
remove the generated input and empty cached state files before recreating the
same environment:

```bash
# Clear the generated tfvars and any cached state
rm -f infra/terraform/terraform.auto.tfvars.json
rm -f infra/terraform/terraform.tfstate*

# Then start from Module 2
./scripts/anyscale-aks.sh apply
```

Example output:

```text
Plan: <resource-count> to add, 0 to change, 0 to destroy.
```

The `.env` file is unchanged, so the same values carry over. Terraform will
create the environment again from those settings.

## What you proved

You created a public AKS cluster in Region A, connected a Flex node from Region B,
connected Anyscale on Azure, and ran a distributed workload across both locations.
For the GPU path, the proof file showed two CUDA workers in the same training run,
one on managed AKS and one on Flex. The cleanup checks then confirmed that the
Azure resources and Terraform state were removed.
