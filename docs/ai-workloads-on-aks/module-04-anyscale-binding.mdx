In this setup, you will register the AKS cluster as an Anyscale cloud. An
Anyscale **cloud** combines the Kubernetes target with its storage, identity, and
compute settings. You will install the AKS operator extension, assign user RBAC,
and check the Gateway API path that exposes Ray services.

## What You Will Do

You will create the Anyscale on Azure cloud resource for the AKS cluster, install
its Azure-managed operator extension, and confirm the deploying user has the
Anyscale Platform administrator role needed for the preview control plane. Before
you move on, you will check the operator pod and confirm that the Gateway API
resource reports `Programmed=True`.

## Background: Anyscale on AKS

Anyscale on AKS is available through Azure-native resources and an AKS cluster extension.
The extension installs the Anyscale operator in the `anyscale-operator` namespace and
connects it to the Anyscale control plane at `console.azure.anyscale.com`.

When you submit a Ray job, Anyscale places Ray head and worker pods on nodes that
match the compute config's resource requirements. Because the Flex host is a standard
Kubernetes node, Anyscale can schedule onto it without workload code changes.

:::info Preview feature
Anyscale on Azure is currently in public preview. If you encounter unexpected
behavior, save the job status, logs, and Kubernetes placement data before
opening an issue.
:::

## Step 1: Confirm regional support

The Anyscale operator AKS extension is not available in every region or
subscription. Run this command against the AKS cluster before enabling Anyscale.
It asks Azure which Anyscale operator extension types the cluster can install:

```bash
source .env
RG="rg-${TF_VAR_project}-${TF_VAR_environment}-${TF_VAR_region_short}"
CLUSTER="aks-${TF_VAR_project}-${TF_VAR_environment}-${TF_VAR_region_short}"

az k8s-extension extension-types list-by-cluster \
  --resource-group "$RG" \
  --cluster-name "$CLUSTER" \
  --cluster-type managedClusters \
  --query "[?name=='anyscale.aks.operator' || name=='preview.anyscale.aks.operator'].{name:name}" \
  -o json
```

Expected non-empty result:

```json
[
  {
    "name": "anyscale.aks.operator"
  }
]
```

:::caution If Azure returns an empty array
An empty array means the current Region A and subscription combination does not
support the operator extension. Do not enable Anyscale or continue with the
current AKS cluster. Redeploy AKS in a region where the query returns
`anyscale.aks.operator` or `preview.anyscale.aks.operator`. Attempting the
deployment in an unsupported region produces an error like this:

```text
ExtensionTypeRegistrationGetFailed: Extension type '<extension-type>'
is not supported in region '<region>' for cluster type: ManagedClusters.
```

:::

## Step 2: Authenticate to Anyscale

The bootstrap command installed the Anyscale CLI in `.venv`, so you do not need
to activate the virtual environment first. Check the cached session before
starting a new login:

```bash
export ANYSCALE_HOST="https://console.azure.anyscale.com"

if .venv/bin/anyscale cloud list --json --no-interactive >/dev/null 2>&1; then
  echo "PASS: cached Anyscale credentials are valid"
else
  .venv/bin/anyscale login
fi
```

When cached credentials are valid, the command does not open a browser. If they
are missing or expired, `anyscale login` opens your default browser. That browser
handoff is expected; complete authentication there, then return to the terminal.

List the clouds available to the authenticated account:

```bash
.venv/bin/anyscale cloud list
```

The command should return at least one accessible cloud or an empty authenticated
list. An authentication error means the browser login did not complete.

## Step 3: Enable Anyscale

After the command in Step 1 returns an Anyscale operator type, change the existing
Anyscale setting in `.env`:

```bash
TF_VAR_anyscale_enabled="true"
```

Keep the Region A and Region B values selected in Module 1. The environment
template already enables the default Anyscale Platform administrator assignment
for the signed-in Azure user, so you do not need to edit that setting for the
self-guided lab.

Region A must support `anyscale.aks.operator` or
`preview.anyscale.aks.operator` for your subscription. Region B must have quota
for the selected Flex VM, and the peering created in Module 2 connects the two
networks.

The operator and workloads use federated workload identity to access Azure
services without a stored storage key or SAS token. This is separate from the
Anyscale Platform administrator role that lets the deploying user use the
preview control plane.

## Step 4: Deploy the Anyscale cloud and operator

Terraform creates the `Anyscale.Platform` cloud resource, then installs the
Azure-managed AKS operator extension and binds it to that cloud. The Anyscale on
Azure resource provider is currently a preview service.

With `.env` configured correctly (region and `TF_VAR_anyscale_enabled="true"`), deploy:

```bash
./scripts/anyscale-aks.sh apply
```

This creates the Anyscale on Azure cloud resource through AzAPI, assigns the
current principal the `Anyscale Platform Administrator Role` at subscription scope,
and passes the cloud deployment ID to the AKS operator extension. The extension's
Marketplace plan is part of this bound deployment, not a separate onboarding path.
Terraform enables the AKS-managed Gateway controller and waits until its
`approuting-istio` class and authenticated Kubernetes API access are stable. It
then prepares Gateway API ingress for Ray services and creates the Workload
Identity federation and Kubernetes RBAC bindings the operator needs.

Example completion lines:

```text
azapi_resource.anyscale_platform[0]: Creation complete
azurerm_role_assignment.anyscale_platform["current_principal_admin"]: Creation complete
azurerm_kubernetes_cluster_extension.anyscale_operator: Creation complete
Apply complete!
```

Expected duration: **10-15 minutes** (the first operator installation can take
several minutes).

:::caution Anyscale user access is required
The deployment assigns the signed-in Azure principal the built-in
`Anyscale Platform Administrator Role` at subscription scope by default. This is separate
from Kubernetes RBAC and from the workload identity data-plane roles used by jobs. Keep
`TF_VAR_anyscale_platform_default_admin_assignment` enabled unless an
administrator pre-creates an equivalent assignment for you.
:::

After the deployment finishes, confirm that the extension reports `Succeeded`:

**Check the extension:** the result should show `Succeeded` and report the
installed version.

```bash
source .env
RG="rg-${TF_VAR_project}-${TF_VAR_environment}-${TF_VAR_region_short}"
CLUSTER="aks-${TF_VAR_project}-${TF_VAR_environment}-${TF_VAR_region_short}"

az k8s-extension show \
  --cluster-name "$CLUSTER" \
  --resource-group "$RG" \
  --cluster-type managedClusters \
  --name anyscale-operator \
  --query '{name:name,provisioningState:provisioningState,currentVersion:currentVersion}' -o json
```

Expected fields:

```json
{
  "name": "anyscale-operator",
  "provisioningState": "Succeeded",
  "currentVersion": "<installed-version>"
}
```

Verify the user-side Anyscale Platform RBAC assignment:

**Check your access:** the result should show the signed-in Azure user with the
Anyscale Platform Administrator role at subscription scope.

```bash
PRINCIPAL_ID="$(az ad signed-in-user show --query id -o tsv)"

az role assignment list \
  --assignee "$PRINCIPAL_ID" \
  --scope "/subscriptions/$TF_VAR_azure_subscription_id" \
  --query "[?roleDefinitionName=='Anyscale Platform Administrator Role'].{role:roleDefinitionName,scope:scope}" \
  -o table
```

Expected row:

```text
Role                                  Scope
------------------------------------  -------------------------------------------------
Anyscale Platform Administrator Role  /subscriptions/<your-subscription-id>
```

Run the Module 4 check to inspect the extension, operator, and user role together:

**Check all required Anyscale resources:** all four lines should report `PASS`.
If one fails, use its name to identify whether the extension, namespace,
operator pod, or user role needs attention.

```bash
./scripts/validate-lab.sh m4
```

Expected output includes:

```text
PASS M4-01 Azure extension provisioning succeeded
PASS M4-02 anyscale-operator namespace active
PASS M4-03 operator pods healthy
PASS M4-04 current principal has Anyscale Platform Administrator Role at subscription scope
```

## Step 5: Verify the Anyscale operator and Gateway

The deployment creates `anyscale-operator/anyscale-gateway` after the operator
extension connects to the Anyscale cloud. The Gateway must report
`Programmed=True` before Anyscale can expose Ray services.

**Check the operator and Gateway:** inspect them together, then read the Gateway
condition directly.

```bash
kubectl get pods,gateway -n anyscale-operator -o wide
```

Example output:

```text
NAME                                     READY   STATUS    RESTARTS   AGE   IP
pod/anyscale-operator-<pod-suffix>        3/3     Running   0          <age> <pod-ip>

NAME                                                CLASS              ADDRESS        PROGRAMMED   AGE
gateway.gateway.networking.k8s.io/anyscale-gateway  approuting-istio   <gateway-ip>   True         <age>
```

Confirm the Gateway has been programmed:

```bash
kubectl get gateway anyscale-gateway \
  -n anyscale-operator \
  -o jsonpath='{.status.conditions}'
```

Expected condition:

```json
[{"type":"Programmed","status":"True","reason":"Programmed"}]
```

Confirm the cloud is visible in the console:

**Check the cloud record:** the authenticated Anyscale account should find the
Azure-backed cloud with the expected provider, compute stack, and region.

```bash
source .env
CLOUD="${TF_VAR_project}-${TF_VAR_environment}-${TF_VAR_region_short}"
ANYSCALE_HOST=https://console.azure.anyscale.com \
  .venv/bin/anyscale cloud list --json --no-interactive --max-items 100 |
  jq -e --arg cloud "$CLOUD" \
    'first(.[] | select((.name | split("/") | last) == $cloud)) | {id, name: (.name | split("/") | last), provider, compute_stack, region}'
```

Example output:

```json
{
  "id": "<cloud-id>",
  "name": "flexany-dev-<region-a-short>",
  "provider": "AZURE",
  "compute_stack": "K8S",
  "region": "<region-a-azure-name>"
}
```

## Step 6: Review where the workload will run

The distributed Ray job uses this placement:

| Step | CPU path | GPU path |
| --- | --- | --- |
| Head pod | AKS CPU node in Region A | AKS CPU node in Region A |
| Worker pod | Flex node `agentpool=aksflexnodes` in Region B | GPU-capable Flex node `agentpool=aksflexnodes` in Region B |
| DNS policy | Normal `ClusterFirst` | Normal `ClusterFirst` after GPU enablement |

Do not submit the workload until managed Cilium, Unbounded Flex networking, the
operator, and Gateway readiness checks pass. The CPU path then runs
`./scripts/run-anyscale-workload.sh --mode cpu`.

For the GPU path, continue only after you confirm quota and capacity for the GPU
VM size selected in `.env` and the readiness checks show `nvidia.com/gpu`
allocatable on the Flex node.

## Success evidence

You can move on when the `Anyscale.Platform` resource provider is registered, the
Anyscale cloud is visible to the authenticated CLI with the expected Azure and
Kubernetes fields, the AKS extension reports `Succeeded`, the Gateway has
`Programmed=True`, and the placement table still sends workers to
`agentpool=aksflexnodes`. Together, these results show that Azure, Kubernetes,
and Anyscale are connected before any workload runs.
