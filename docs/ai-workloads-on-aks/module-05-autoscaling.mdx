Before you submit the workload, confirm that every part of its path is healthy.
You will check how the CPU pool scales, how services route between AKS and Flex,
Flex DNS, and the Anyscale Gateway without starting a Ray job.

## What You Will Do

You will review the scaling bounds on the Region A CPU node pool and see how they
differ from the fixed Flex host capacity. Then you will rerun the network, DNS,
HTTPS, and Anyscale Gateway checks so the workload starts from a healthy cluster
state. If you enabled the GPU path, you will install the NVIDIA device plugin and
confirm that both GPU nodes report an allocatable `nvidia.com/gpu`.

## Understanding the capacity model

Your environment has two distinct compute locations:

| Location | Managed by | Scales how |
| ---------- | ----------- | ------------ |
| Region A AKS CPU pool (`cpu`) | [AKS cluster autoscaler](https://learn.microsoft.com/en-us/azure/aks/cluster-autoscaler) | Adds nodes when resource constraints leave a pod unschedulable, within the pool's configured bounds |
| Region B Flex host | You provisioned and joined it to AKS | Fixed capacity, already `Ready` |

The Flex host does **not** autoscale. It is pre-provisioned and remains fixed
while this environment exists. The Kubernetes scheduler can place workers on it
immediately without waiting for a scale event.

The VM size sets nominal CPU and memory, but Kubernetes schedules pods against
the lower allocatable values reported by each node. AKS
[resource reservations](https://learn.microsoft.com/en-us/azure/aks/core-aks-concepts#resource-reservations)
make allocatable capacity lower than the VM's total capacity because the
operating system and cluster services need CPU and memory. The Anyscale pod also
runs helper containers alongside the main one, which consume some of that
remainder. In Module 6, the workload command reads
every eligible Ready node, uses the smallest allocatable value, reserves `500m`
CPU and `1Gi` memory for node services and helper containers, and rounds down to
whole CPUs and GiB. This shared calculation applies to CPU and GPU mode, so
changing a supported VM size does not require a compute-config edit.

The smoke workload caps each derived request at its useful target instead of
claiming all capacity on a larger VM:

| Role | CPU target | Memory target | Minimum after headroom |
| --- | --- | --- | --- |
| Ray head, both paths | 2 | `8Gi` | 1 CPU and `4Gi` |
| Managed and Flex CPU workers | 2 | `8Gi` | 1 CPU and `4Gi` |
| Managed and Flex GPU workers | 4 | `16Gi` | 1 CPU and `8Gi` |

If the live capacity falls below a minimum, the workload command stops before it
submits an Anyscale Job. The optional
`ANYSCALE_RESULTS_NODE_CPU_HEADROOM_MILLICORES` and
`ANYSCALE_RESULTS_NODE_MEMORY_HEADROOM_GIB` values in `.env` change the reserve,
not the selected VM size or workload target.

:::warning Flex capacity remains allocated
The AKS CPU pool can scale within its configured bounds. The Flex VM stays
allocated until you remove the environment in Module 7, even when no worker pod
is running.
:::

## Step 1: Review the AKS CPU pool

```bash
source .env
RG="rg-${TF_VAR_project}-${TF_VAR_environment}-${TF_VAR_region_short}"
CLUSTER="aks-${TF_VAR_project}-${TF_VAR_environment}-${TF_VAR_region_short}"

az aks nodepool list \
  --resource-group "$RG" \
  --cluster-name "$CLUSTER" \
  --query '[].{Name:name,VmSize:vmSize,Count:count,MinCount:minCount,MaxCount:maxCount,Mode:mode}' \
  -o table
```

This CPU run used the shared worker SKU selected in Module 1 and printed:

```text
Name    VmSize             Count    MinCount    MaxCount    Mode
------  -----------------  -------  ----------  ----------  ------
sys     Standard_D4s_v5    1        1           3           System
cpu     Standard_D4ads_v6  1        1           4           User
```

Compare the live `VmSize`, `MinCount`, and `MaxCount` values with the system and
CPU pool settings in `.env`. Those selected sizes and upper bounds, not the
example values above, determine the Region A quota required by your environment.

## Step 2: Review the CPU or GPU capacity profile

### CPU path

```bash
grep -E '^(TF_VAR_cpu_vm_size|TF_VAR_gpu_pool_configs)=' .env
```

For the same CPU run, the active fields were:

```text
TF_VAR_cpu_vm_size="Standard_D4ads_v6"
TF_VAR_gpu_pool_configs='{}'
```

Your CPU VM size can differ based on the shared candidate you selected in
Module 1.

Use the live pool table from Step 1 to read the minimum and maximum node counts.
The CPU VM size in `.env` provides the resources for the Ray head, and the Module
1 quota result shows whether the selected size and pool bounds fit the current
subscription.

### GPU path: Review the driver and device plugin settings

Choose the GPU path before provisioning the Flex host. If you are continuing
from a CPU-only host, changing the Flex VM size or image will replace that host.
Start with a new environment when you want to switch paths without replacing an
existing VM.

Review the GPU values you selected in Module 1 for both node domains:

```bash
grep -E '^(TF_VAR_gpu_pool_configs|TF_VAR_flex_host_vm_size|TF_VAR_flex_host_source_image_reference|ANYSCALE_FLEX_GPU_ENABLED|ANYSCALE_RESULTS_GPU_PRODUCT_LABEL)=' .env
```

Enable this path only after you confirm quota for one managed GPU VM in Region A
and one GPU Flex VM in Region B. Keep both GPU counts fixed at one. Module 6
requires one Ray Train worker in each domain.

### CPU and GPU paths: Review live allocatable capacity

This table shows the values that Kubernetes can schedule after Azure and AKS
reserve resources on each selected VM. Module 6 reads these same fields when it
creates the Anyscale compute config.

```bash
kubectl get nodes \
  -o custom-columns='NODE:.metadata.name,POOL:.metadata.labels.agentpool,READY:.status.conditions[?(@.type=="Ready")].status,CPU:.status.allocatable.cpu,MEMORY:.status.allocatable.memory,GPU:.status.allocatable.nvidia\.com/gpu'
```

The live CPU run showed one managed CPU node, one system node, and one Flex
node. Node suffixes and memory reservations can differ in your cluster:

```text
NODE                          POOL           READY   CPU     MEMORY       GPU
aks-cpu-13577184-vmss000000   cpu            True    3860m   12073732Ki   <none>
aks-sys-33810774-vmss000000   sys            True    3860m   12072716Ki   <none>
vm-flex-flexany-e2e814-scus   aksflexnodes   True    3860m   13967052Ki   <none>
```

Every node used by your selected path should show `True` under `READY`. The CPU
and memory columns should reflect the live node SKU but can be lower than the
VM specification. Before Step 4 installs the NVIDIA device plugin, the GPU
column can be blank. After the installation completes, the managed GPU node and
Flex node must each show `1` under `GPU`.

## Step 3: Apply the capacity settings

```bash
./scripts/anyscale-aks.sh apply
```

For the CPU path, this confirms that the Anyscale resources and fixed CPU
autoscaling bounds match `.env`. If you changed the Flex host VM size or image
for the GPU path, Terraform will replace the Flex host so the new GPU-capable
image can boot.

Example output when the profile has not changed:

```text
Apply complete! Resources: 0 added, 0 changed, 0 destroyed.
```

If you intentionally changed the Flex host VM size or image for the GPU path,
review the replacement shown by Terraform instead of expecting this no-change
summary.

## Step 4: Check that the workload path is ready

### GPU path

Skip this subsection for the CPU path. If you enabled the GPU path, first confirm
the Flex host driver and then install the NVIDIA device plugin before running the
shared readiness checks. The installation script targets the managed GPU pool
and the Flex node and adds the required
[taint tolerations](https://kubernetes.io/docs/concepts/scheduling-eviction/taint-and-toleration/).

```bash
source .env
ssh -i "$SSH_PRIVATE_KEY_PATH" \
  "${TF_VAR_flex_host_admin_username}@$(./scripts/anyscale-aks.sh output -raw flex_host_public_ip)" \
  'nvidia-smi --query-gpu=name,driver_version --format=csv,noheader'
```

Example output:

```text
<gpu-name>, <driver-version>
```

The installation script labels the Flex node with
`nvidia.com/gpu.product` from `ANYSCALE_RESULTS_GPU_PRODUCT_LABEL`. Terraform
sets the managed pool's product label from `TF_VAR_gpu_pool_configs`.

```bash
./scripts/install-nvidia-device-plugin.sh
```

Expected output:

```text
daemonset.apps/nvidia-device-plugin-daemonset configured
daemon set "nvidia-device-plugin-daemonset" successfully rolled out
NVIDIA device plugin ready: 1 allocatable GPU in <managed-gpu-pool> and 1 in aksflexnodes
```

### CPU and GPU paths

Run the readiness checks for the CPU pool bounds, the selected GPU settings, the
AKS network profile, Flex pod networking, [`ClusterFirst` DNS](https://kubernetes.io/docs/concepts/services-networking/dns-pod-service/#pod-s-dns-policy),
HTTPS access, pod and [`ClusterIP` Service](https://kubernetes.io/docs/concepts/services-networking/service/#type-clusterip)
traffic in both directions, and the Anyscale extension and Gateway:

```bash
./scripts/validate-lab.sh m5
```

The live CPU run printed this readiness summary. Your Flex node name and Gateway
address will differ:

```text
PASS M5-01 CPU node pool autoscaling configured
SKIP M5-02 GPU path disabled in current env profile
PASS AKS no-CNI network profile is active; podCidr=10.244.0.0/16
PASS AKS no-CNI path is active for the Unbounded lab flow
PASS Flex node vm-flex-flexany-e2e814-scus Ready in southcentralus
PASS Unbounded owns the no-CNI AKS and Flex networking path
PASS Flex ClusterFirst DNS resolves Anyscale and Kubernetes service names
PASS Flex pod HTTPS egress reaches console.azure.anyscale.com
PASS Unbounded connectivity: bilateral pod traffic and ClusterIP routing from AKS and Flex
PASS Anyscale extension and operator pods ready
PASS Gateway anyscale-operator/anyscale-gateway programmed at 20.80.176.35
```

The command writes pod logs and Kubernetes JSON under
`.cache/lab-validation/m5-flex-network/`. If a check fails, use that directory first;
it contains the short-lived diagnostic pod output before cleanup. A node or
pod-network failure points to the saved node, network profile, and Unbounded site
records. A DNS, HTTPS egress, or cross-node traffic failure points to the
matching diagnostic pod log. Stop before submitting a workload, correct the
problem, and rerun `./scripts/validate-lab.sh m5` until every required check
reports `PASS`.

## Step 5: Inspect Anyscale service health

The readiness command already checked these resources. Use the following commands
when you want to inspect the extension and Gateway directly.

```bash
source .env
RG="rg-${TF_VAR_project}-${TF_VAR_environment}-${TF_VAR_region_short}"
CLUSTER="aks-${TF_VAR_project}-${TF_VAR_environment}-${TF_VAR_region_short}"

az k8s-extension show \
  --cluster-name "$CLUSTER" \
  --resource-group "$RG" \
  --cluster-type managedClusters \
  --name anyscale-operator \
  --query '{name:name,provisioningState:provisioningState,currentVersion:currentVersion}' -o json

kubectl get pods,gateway -n anyscale-operator -o wide
```

The live service check showed extension version `1.7.1`, a healthy three-container
operator pod, two Gateway proxy pods, and a programmed Gateway. Pod suffixes,
addresses, and ages change between deployments:

```text
{
  "currentVersion": "1.7.1",
  "name": "anyscale-operator",
  "provisioningState": "Succeeded"
}

NAME                                                     READY   STATUS
pod/anyscale-gateway-approuting-istio-7cbb874b75-4wppr   1/1     Running
pod/anyscale-gateway-approuting-istio-7cbb874b75-9jmc7   1/1     Running
pod/anyscale-operator-5978b9674b-fmcbm                   3/3     Running

NAME                                                 CLASS              ADDRESS        PROGRAMMED
gateway.gateway.networking.k8s.io/anyscale-gateway   approuting-istio   20.80.176.35   True
```

:::warning Resolve failed checks before continuing
Do not submit the workload if any check above fails. Ray services need healthy
Unbounded routing, ClusterFirst DNS, and an available Anyscale Gateway.
:::

## Step 6: Verify that no workload pods remain on Flex

```bash
source .env
FLEX_NODE="vm-flex-${TF_VAR_project}-${TF_VAR_environment}-${TF_VAR_flex_region_short}"
kubectl get pods -A -o wide --field-selector spec.nodeName="$FLEX_NODE"
```

CPU path example output:

```text
NAMESPACE          NAME                                  READY   STATUS    NODE
unbounded-system   unbounded-net-kube-proxy-flex-vqjt4   1/1     Running   vm-flex-flexany-e2e814-scus
unbounded-system   unbounded-net-node-75nwb              1/1     Running   vm-flex-flexany-e2e814-scus
```

Your pod suffixes and Flex node name will differ. If the listing immediately
after `validate-lab.sh m5` also shows a diagnostic route pod in `Terminating`,
rerun the listing. Continue when cleanup finishes and only the expected system
pods remain.

The GPU path also includes the NVIDIA device-plugin pod installed in Step 4:

```text
kube-system   nvidia-device-plugin-daemonset-abcde   1/1   Running   <flex-node-name>
```

Before submission, the CPU path should show the Unbounded node and Flex
kube-proxy system pods, while the GPU path should also show the NVIDIA device
plugin. No AKS-managed networking daemon set should run on the Flex node. Any
application or prior Ray workload pod is left over from an earlier run and should
finish or be removed before you continue.

## Validate cluster readiness

You can move on when `./scripts/validate-lab.sh m5` prints `PASS` for the
CPU scale profile, Flex node readiness, Flex DNS, Flex HTTPS egress, AKS-to-Flex
pod reachability, and Anyscale Gateway health. If the GPU path is enabled, the
same command must also report allocatable `nvidia.com/gpu` on the managed GPU
pool and on `aksflexnodes`.
