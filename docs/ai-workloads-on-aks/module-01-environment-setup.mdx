Before you deploy anything, confirm that your workstation and Azure subscription
can support the path you chose. You will authenticate, check regional quota, and
save the settings that every deployment and workload command uses.

## What You Will Do

You will verify that your workstation has the required tools, confirm Azure quota
for the path you plan to run, and create the local `.env` file that drives the
rest of the lab. This is also where you choose the CPU or GPU Flex path that your
Azure environment supports before Terraform creates any resources.

## Regional Prerequisites

You will use two Azure regions so the Ray head and worker can run in different
locations. Region A hosts AKS and must support the Anyscale operator extension.
Region B hosts the external Flex VM and needs capacity for the VM size you choose.

| Lab name | Value in `.env` | What runs there |
| --- | --- | --- |
| Region A | `TF_VAR_azure_location` | Public AKS cluster, storage, ACR, and Anyscale operator extension |
| Region B | `TF_VAR_flex_region` | Flex host and Ray worker for the selected CPU or GPU path |

The names Region A and Region B stay the same throughout the guide. Their actual
Azure location values can differ between lab environments. Choose Region A based
on Anyscale extension availability, then choose a reachable Region B with quota
and capacity for the Flex host.

:::caution Region A must support the Anyscale extension
Choose Region A with Anyscale operator availability in mind. After Module 2
creates AKS, Module 4 checks whether that cluster can install the Anyscale
operator extension. If Azure returns no supported extension type, redeploy AKS
in a supported Region A. Region B does not affect this check.
:::

## Step 1: Clone the lab repository

```bash
git clone https://github.com/KenKilty/aks-flex-anyscale-lab.git aks-flex-anyscale-sample
cd aks-flex-anyscale-sample
```

This directory name keeps the commands in the rest of the lab independent of
where you store your other repositories.

## Step 2: Create the local lab environment

```bash
./scripts/anyscale-aks.sh bootstrap
```

The command creates `.env` from `.env-template`, records the subscription and
tenant from your current Azure CLI session, creates the SSH key configured by
`SSH_PRIVATE_KEY_PATH` when it is missing, and installs the Anyscale CLI in
`.venv`. It does not deploy Azure resources.

Expected final lines:

```text
azure subscription: <your-subscription-id>
azure tenant: <your-tenant-id>
Anyscale CLI: <repository-path>/.venv/bin/anyscale
next: ./scripts/anyscale-aks.sh doctor
```

Keep `.env` for the full lab. It is ignored by Git and drives every deployment,
workload, and teardown command.

## Step 3: Verify your Azure region and VM-size settings in `.env`

Open `.env` and verify that the four Azure ID values match `az account show`.
Set `TF_VAR_azure_location` and `TF_VAR_region_short` to the actual Azure name
and short label for Region A. Set `TF_VAR_flex_region` and
`TF_VAR_flex_region_short` for Region B. Set the CPU or GPU VM sizes for the path
available in your Azure environment, and keep
`TF_VAR_cilium_pod_cidr="10.83.0.0/16"` for AKS-managed pods and
`TF_VAR_unbounded_flex_pod_cidr="10.84.0.0/16"` for Flex pods. The ranges must
not overlap each other, either VNet, or the service CIDR. The Flex host is
enabled by default because every lab path uses it.

These values are the local environment profile used by every wrapper command:

| Setting | What it controls | Where you use it next |
| --- | --- | --- |
| `TF_VAR_azure_location` and `TF_VAR_region_short` | Region A and the AKS resource names | Module 2 creates AKS; Module 4 checks Anyscale extension availability here. |
| `TF_VAR_flex_region` and `TF_VAR_flex_region_short` | Region B and the Flex host resource names | Module 2 creates the VNet and Flex VM here; Module 3 joins the VM to AKS. |
| `TF_VAR_cilium_pod_cidr` and `TF_VAR_unbounded_flex_pod_cidr` | Separate pod address ranges for AKS-managed nodes and Flex nodes | Module 2 configures Azure CNI Overlay; Module 3 verifies Unbounded IPAM and cross-site routing. |
| `TF_VAR_system_vm_size` and `TF_VAR_cpu_vm_size` | The AKS system and CPU node pools | This step checks their Region A quota before Module 2 creates them. |
| `TF_VAR_flex_host_vm_size` and `TF_VAR_flex_host_source_image_reference` | The CPU or GPU Flex VM and its host image | Module 2 creates this VM; Module 3 joins it to AKS. |
| `TF_VAR_anyscale_enabled` | Whether Terraform creates the Anyscale cloud, extension, and Gateway | Keep it `"false"` until Module 4 confirms Region A support. |

## Step 4: Check local tools and Azure access

```bash
./scripts/anyscale-aks.sh doctor
```

Expected output:

```json
{
  "subscription": "<your-subscription-id>",
  "tenant": "<your-tenant-id>",
  "user": "<your-user>"
}
```

If this fails, read the named missing command, install it, and retry. If the
Anyscale CLI is missing, rerun `./scripts/anyscale-aks.sh bootstrap`.

## Step 5: Check Azure quota for your chosen path

Use this helper to find the quota family for a VM size selected in `.env`, then
show its current usage and limit:

```bash
source .env

check_vm_quota() {
  local location="$1"
  local vm_size="$2"
  local family

  family="$(az vm list-skus \
    --location "$location" \
    --resource-type virtualMachines \
    --size "$vm_size" \
    --all \
    --query '[0].family' \
    -o tsv)"

  printf '\n%s in %s uses quota family %s\n' "$vm_size" "$location" "$family"
  az vm list-usage \
    --location "$location" \
    --query "[?name.value=='${family}']" \
    -o table
}
```

### CPU path

Check the AKS system and CPU pool sizes in Region A, then the Flex host size in
Region B:

```bash
check_vm_quota "$TF_VAR_azure_location" "$TF_VAR_system_vm_size"
check_vm_quota "$TF_VAR_azure_location" "$TF_VAR_cpu_vm_size"
check_vm_quota "$TF_VAR_flex_region" "$TF_VAR_flex_host_vm_size"
```

Each command should return the quota family selected by its `TF_VAR_*_vm_size`:

```text
<selected-vm-size> in <region> uses quota family <quota-family>
CurrentValue    Limit    Unit    LocalName
--------------  -------  ------  --------------------------
<current>       <limit>  Count   <selected VM quota family>
```

Subtract `CurrentValue` from `Limit` and confirm the remaining quota can create
the selected nodes. Use the minimum and maximum node counts in `.env` for the
AKS system and CPU pools, and reserve one Flex host in Region B. If the system
and CPU VM sizes use the same quota family, include the maximum capacity of both
pools in that calculation. The values differ by subscription and region.

### GPU path

Check the GPU Flex host size selected in `.env`:

```bash
check_vm_quota "$TF_VAR_flex_region" "$TF_VAR_flex_host_vm_size"
```

If the selected GPU VM family has insufficient quota or the VM size is
unavailable, choose another GPU VM size or reachable Region B. Update the
matching `.env` values before deploying AKS.

:::tip Quota increase
If your CPU quota is low, request an increase at
[Azure Quotas](https://portal.azure.com/#view/Microsoft_Azure_Capacity/QuotaMenuBlade)
before continuing. GPU quota can be requested later if you want to extend the lab.
:::

## Step 6: Set your CPU or GPU path

| Step | CPU path | GPU path |
| --- | --- | --- |
| Module sequence | CPU workload path | GPU workload path |
| Region A | Value of `TF_VAR_azure_location` | Same Region A; must support the Anyscale AKS extension |
| Region B | Value of `TF_VAR_flex_region` | Same role, with quota and capacity for the selected GPU VM size |
| Workload | CPU-only Ray worker on Flex | `GPU:1` Ray worker on the GPU Flex host |

:::caution Choose the host profile before creating it
The selected path determines the Flex VM size and source image. Changing a live
CPU Flex host to a GPU VM or GPU-ready image makes Terraform replace that host.
Use a new environment when you want to switch paths without replacing an
existing host. The CPU path is the lower-cost first run; use the GPU path only
after the Region B quota check succeeds.
:::

For the CPU path, open `.env` and confirm these existing values. Replace them if
you changed regions while checking quota:

```bash
TF_VAR_azure_location="<region-a-azure-name>"
TF_VAR_region_short="<region-a-short>"
TF_VAR_flex_region="<region-b-azure-name>"
TF_VAR_flex_region_short="<region-b-short>"
```

The template already uses no AKS GPU pool and keeps Anyscale disabled until
Module 4 checks extension availability against the deployed AKS cluster. You do
not need to edit those settings for the CPU path.

For the GPU path, keep the Region B values that passed the quota check and replace
the corresponding host assignments in `.env` with the values supplied for your
Azure environment:

```bash
TF_VAR_flex_host_vm_size="<gpu-vm-size>"
TF_VAR_flex_host_source_image_reference='<gpu-ready-source-image-reference-json>'
ANYSCALE_FLEX_GPU_ENABLED="true"
ANYSCALE_RESULTS_GPU_PRODUCT_LABEL="<kubernetes-gpu-product-label>"
```

The GPU source image must already include NVIDIA drivers for the selected VM
size. Use the exact image reference supplied for your Azure environment. Module
5 verifies those drivers, then installs the Kubernetes NVIDIA device plugin that
advertises the GPU to workloads. The template already targets the Flex node and
starts one GPU worker. Increase the worker count only when the selected VM
exposes enough GPUs.

:::caution Complete the environment first
Wait until managed Cilium, the Flex node's Unbounded network, DNS, and the
Anyscale Gateway all pass their readiness checks before running the Anyscale
workload.
:::

## Success evidence

Run the environment check and save a timestamped report:

```bash
./scripts/anyscale-aks.sh doctor | tee .cache/env-check-$(date +%Y%m%d-%H%M%S).json
```

Save this file with the Step 5 quota output. Together, they record which Azure
subscription and regions you checked. If a later command targets the wrong
subscription or reports insufficient quota, compare it with these initial results.
