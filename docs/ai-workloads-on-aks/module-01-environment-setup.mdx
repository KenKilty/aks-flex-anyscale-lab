Before you deploy anything, choose which version of the lab you want to run. The
CPU option runs a small CPU-only training job. The GPU option runs distributed
GPU training across an AKS-managed GPU node and the Flex node VM.

If you have not read [Key Concepts](./key-concepts), start there. It explains
Ray, AKS Flex Node, and Anyscale and provides background for concepts used
throughout the lab.

## What You Will Do

You will sign in to Azure, select the subscription for the lab, and create a
Git-ignored `.env` configuration file. You will choose two regions, ask Azure
which shared CPU or GPU VM SKUs have quota in both, and save one of those SKUs
for the workers in both regions.

Choosing CPU or GPU also chooses the type of Flex node VM that Terraform builds
in Module 2. CPU-only training uses CPU capacity in both regions. GPU training
uses one GPU worker in each region.

## Choose two Azure regions

This lab uses two Azure regions so that the [Ray head and its
workers](./key-concepts) run in different locations. The instructions use the
generic names Region A and Region B because you choose the Azure regions that
your subscription supports and where you have enough quota:

| Lab name | What runs there | Value in `.env` |
| --- | --- | --- |
| Region A | Public AKS cluster, storage, ACR, and the Anyscale operator extension | `TF_VAR_azure_location` |
| Region B | The Flex node VM and its Ray worker | `TF_VAR_flex_region` |

Region A must support Anyscale on Azure. Region B can be any Azure region where
your subscription has quota for the configured Flex node VM. You select both
regions after you sign in and create the local configuration file.

:::caution Region A must support Anyscale on Azure
Step 4 lists the regions accepted by the `Anyscale.Platform` resource provider.
Later in Module 4, you run a separate check against the deployed AKS cluster to
confirm that it can install the Anyscale operator extension. Region B does not
need that extension.
:::

## Step 1: Clone the lab repository

```bash
git clone https://github.com/KenKilty/aks-flex-anyscale-lab.git aks-flex-anyscale-sample
cd aks-flex-anyscale-sample
```

Open the cloned `aks-flex-anyscale-sample` folder in Visual Studio Code. From the
current shell, you can run:

```bash
code .
```

If the `code` command is unavailable, select **File > Open Folder** in Visual
Studio Code and choose `aks-flex-anyscale-sample`.

In Visual Studio Code, select **Terminal > New Terminal**. The terminal should
open in the repository root. Confirm it before continuing:

```bash
pwd
```

The path should end with `aks-flex-anyscale-sample`. Run the remaining lab
commands from this terminal.

## Step 2: Sign in to Azure

The bootstrap command reads your active Azure CLI account, so authenticate from
the Visual Studio Code terminal before you run it:

```bash
az login
```

Azure CLI opens a browser for authentication. See [Sign in with Azure
CLI](https://learn.microsoft.com/cli/azure/authenticate-azure-cli-interactively)
if the browser does not open or your organization requires a specific tenant.

Check the account that will own the lab resources:

```bash
az account show \
   --query '{subscription:name,subscriptionId:id,tenantId:tenantId,user:user.name}' \
   --output table
```

If the command shows the wrong subscription, list the subscriptions available
to your account and select the correct one:

```bash
az account list --output table
az account set --subscription "<subscription-name-or-id>"
```

Run `az account show` again after changing the subscription. For more help, see
[Manage Azure subscriptions with Azure
CLI](https://learn.microsoft.com/cli/azure/manage-azure-subscriptions-azure-cli)
and [Troubleshoot Azure
CLI](https://learn.microsoft.com/cli/azure/use-azure-cli-successfully-troubleshooting).

## Step 3: Create the local lab environment

Run the setup command from the Visual Studio Code terminal you opened in Step 1:

```bash
./scripts/anyscale-aks.sh bootstrap
```

The command prepares the local files and tools used in the rest of the lab:

| What it does | Why it matters |
| --- | --- |
| Copies `.env-template` to `.env` if `.env` does not exist | In Step 6, you edit this file to save the regions, shared worker SKU, and other deployment values. |
| Reads the active Azure CLI account and writes one subscription ID and one tenant ID to `.env` | Azure CLI and Terraform use the account you confirmed in Step 2. |
| Creates an SSH key at `SSH_PRIVATE_KEY_PATH` if the key does not exist | Terraform adds the public key to the Flex node VM. Later in Module 3, the setup command uses the private key to copy the node configuration and start the Flex node service. |
| Installs the Anyscale CLI in the repository's `.venv` | Later modules use this repository-local installation for Anyscale commands. |

On success, bootstrap ends with these four lines:

```text
azure subscription: <your-subscription-id>
azure tenant: <your-tenant-id>
Anyscale CLI: <repository-path>/.venv/bin/anyscale
next: choose Region A and Region B, then run ./scripts/anyscale-aks.sh sku-options <region-a> <region-b> cpu|gpu
```

Bootstrap creates `.env` by copying `.env-template`. Git ignores this local
configuration file. The repository scripts load it automatically. Before a
Terraform command runs, the lab script writes its current `TF_VAR_*` values to
`infra/terraform/terraform.auto.tfvars.json`. Terraform reads that generated
file when it plans, creates, or removes the Azure resources. The workload
scripts also load `.env` for the settings they need. When a later step uses an
`.env` variable directly in your terminal, that step tells you to run
`source .env` first.

The choices you make next become these local settings:

| Setting | What it controls | Where you use it next |
| --- | --- | --- |
| `TF_VAR_azure_location` and `TF_VAR_region_short` | Region A and its short resource-name label | Module 2 creates AKS; Module 4 checks Anyscale extension availability here. |
| `TF_VAR_flex_region` and `TF_VAR_flex_region_short` | Region B and its short resource-name label | Module 2 creates the VNet and Flex node VM here; Module 3 joins the VM to AKS. |
| `TF_VAR_aks_pod_cidr` and `TF_VAR_unbounded_flex_pod_cidr` | Separate pod address ranges for AKS-managed nodes and Flex nodes | Module 2 configures AKS with `networkPlugin=none`; Module 3 verifies address assignment and cross-region routing. |
| `TF_VAR_system_vm_size` and `TF_VAR_cpu_vm_size` | The AKS system and CPU node pools | Module 2 creates both pools in Region A. |
| `TF_VAR_flex_host_vm_size` and `TF_VAR_flex_host_source_image_reference` | The CPU or GPU Flex node VM and its image | Module 2 creates this VM; Module 3 joins it to AKS. |
| `TF_VAR_anyscale_enabled` | Whether Terraform creates the Anyscale cloud, extension, and Gateway | Keep it `"false"` until Module 4 confirms Region A support. |

## Step 4: Choose two Azure regions

Choose Region A and Region B before you edit their values in `.env`. The next
step uses both names to find VM SKUs that your subscription can deploy in both
regions.

First, list the regions supported by the `Anyscale.Platform` resource provider:

```bash
az provider show \
  --namespace Anyscale.Platform \
  --query "resourceTypes[?resourceType=='clouds'].locations[]" \
  --output tsv \
  --only-show-errors
```

The command prints the supported display names for Region A. Azure configuration
uses canonical location names such as `westus2`. List both forms, then match a
supported display name to its canonical name:

```bash
az account list-locations \
  --query '[].{Name:name,DisplayName:displayName}' \
  --output table \
  --only-show-errors
```

Set terminal variables to the two canonical names you want to evaluate. This
example uses West US 2 for Region A and South Central US for Region B:

```bash
REGION_A="westus2"
REGION_B="southcentralus"
```

Use your own canonical region names if this pair does not fit your Azure
environment. The SKU command in the next step verifies that
`Anyscale.Platform` supports Region A.

## Step 5: Find a shared VM SKU and check quota

Choose CPU-only training unless your subscription can provide a supported GPU
VM SKU and enough GPU quota in both regions. The lab does not support a mixed
CPU/GPU training layout:

| Option | Region A | Region B |
| --- | --- | --- |
| CPU only | AKS CPU node runs the Ray head and one CPU training worker | CPU Flex node runs the second training worker |
| GPU | AKS CPU node runs the Ray head; AKS GPU node runs one GPU training worker | GPU Flex node runs the second training worker |

### CPU-only SKU candidates

Ask Azure for up to 20 shared CPU candidates with 4-8 vCPUs. The command
excludes restricted SKUs, non-Premium SSD SKUs, and quota families that cannot
provide one VM in each region:

```bash
./scripts/anyscale-aks.sh sku-options "$REGION_A" "$REGION_B" cpu
```

### GPU SKU candidates

List every shared GPU candidate with 4-8 vCPUs that is unrestricted and has
quota for one VM in each region:

```bash
./scripts/anyscale-aks.sh sku-options "$REGION_A" "$REGION_B" gpu
```

Each row shows the SKU's vCPUs, memory, GPU count, quota family, and remaining
family vCPUs in Region A and Region B. Choose one row from the option you plan to
run and keep its exact SKU name. You will use that same worker SKU in both
regions. Azure does not return the Kubernetes GPU product label in this query,
so the GPU option also requires the product label for the accelerator in the SKU
you select.

## Step 6: Save your regions and VM SKU in `.env`

Open `.env` in Visual Studio Code. Bootstrap has already set
`TF_VAR_azure_subscription_id` and `TF_VAR_azure_tenant_id` from the account you
confirmed in Step 2. Replace `change-me` in `TF_VAR_tags` with your name or team.

For a repeat run, replace `dev` in `TF_VAR_environment` with a new 2-6 character
lowercase alphanumeric label before the first Terraform plan. The project,
environment, and Region A label form the resource group name. Keep the same
label through teardown, and do not reuse a label whose resource group still
exists.

Set the region values to the canonical names you chose. Give each region a
concise lowercase label for Azure resource names. For example, abbreviate
`westus2` as `wus2` and `southcentralus` as `scus`:

```bash
TF_VAR_azure_location="westus2"
TF_VAR_flex_region="southcentralus"
TF_VAR_region_short="wus2"
TF_VAR_flex_region_short="scus"
```

Keep each location and its label together. The labels become part of resource
names, so do not change them after the first Terraform apply.

Choose one of the following training options.

### Option 1: CPU only

Set both worker fields to the same CPU SKU you chose from the `sku-options`
output. Keep the separate system-pool SKU supplied by the template unless you
have a reason to change it:

```bash
TF_VAR_cpu_vm_size="<chosen-shared-cpu-vm-sku>"
TF_VAR_gpu_pool_configs='{}'
TF_VAR_flex_host_vm_size="<chosen-shared-cpu-vm-sku>"
ANYSCALE_FLEX_GPU_ENABLED="false"
```

### Option 2: GPU

Use the same chosen GPU SKU for the Region A managed pool and the Region B Flex
node VM. Use the matching Kubernetes GPU product label in both product-label
fields:

```bash
TF_VAR_gpu_pool_configs='{"gpu":{"name":"gpupool","vm_size":"<chosen-shared-gpu-vm-sku>","product_name":"<chosen-kubernetes-gpu-product-label>","gpu_count":"1","min_count":1,"max_count":1,"availability_zones":[]}}'
TF_VAR_flex_host_vm_size="<chosen-shared-gpu-vm-sku>"
ANYSCALE_FLEX_GPU_ENABLED="true"
ANYSCALE_RESULTS_GPU_PRODUCT_LABEL="<chosen-kubernetes-gpu-product-label>"
```

Keep `gpu_count`, `min_count`, and `max_count` at `1`. This creates one managed
GPU worker in Region A and one Flex GPU worker in Region B.

For this option, Terraform installs the [NVIDIA GPU Driver Extension for Linux
VMs](https://learn.microsoft.com/en-us/azure/virtual-machines/extensions/hpccompute-gpu-linux)
on the Ubuntu 24.04 Flex node VM. In Module 5, you install the [NVIDIA device
plugin](https://learn.microsoft.com/en-us/azure/aks/use-nvidia-gpu#nvidia-device-plugin-installation)
on both GPU nodes and verify that each node reports one allocatable GPU.

Confirm that `.env` contains the Region A, Region B, AKS system pool, AKS CPU
pool, and Flex node VM values you chose:

```bash
grep -E '^(TF_VAR_(project|environment|azure_location|flex_region|flex_region_short|system_vm_size|cpu_vm_size|flex_host_vm_size|gpu_pool_configs)|ANYSCALE_FLEX_GPU_ENABLED)=' .env
```

For example, a CPU run using West US 2, South Central US, and a shared
`Standard_D4ads_v6` worker SKU prints these active assignments. Your regions and
SKU can differ based on the candidates Azure returned:

```text
TF_VAR_project="flexany"
TF_VAR_environment="dev"
TF_VAR_azure_location="westus2"
TF_VAR_flex_region="southcentralus"
TF_VAR_flex_region_short="scus"
TF_VAR_system_vm_size="Standard_D4s_v5"
TF_VAR_cpu_vm_size="Standard_D4ads_v6"
TF_VAR_gpu_pool_configs='{}'
TF_VAR_flex_host_vm_size="Standard_D4ads_v6"
ANYSCALE_FLEX_GPU_ENABLED="false"
```

The template keeps Anyscale disabled until Module 4 checks extension
availability against the deployed AKS cluster.

## Step 7: Validate the local configuration

Run `doctor` after saving `.env`:

```bash
./scripts/anyscale-aks.sh doctor
```

The command confirms that `.env` contains the two regions and the shared worker
SKU you selected. It also checks the separate AKS system pool, local tools,
Azure access, network ranges, resource providers, and Anyscale authentication.
If quota changed after Step 5, this check stops before deployment.

When configured pools use the same quota family in one region, `doctor` adds
their minimum vCPU requirements together. GPU pools are checked only when they
are present in `TF_VAR_gpu_pool_configs`.

The command prints one line per check and stops at the first failure. The VM and
quota lines use the values from your environment:

```text
PASS AKS system pool <configured-system-vm-sku> is available in <region-a> (<remaining> <quota-family> vCPUs remain)
PASS AKS CPU pool <configured-cpu-vm-sku> is available in <region-a> (<remaining> <quota-family> vCPUs remain)
PASS Flex host <configured-flex-vm-sku> is available in <region-b> (<remaining> <quota-family> vCPUs remain)
PASS combined minimum for <pools-in-this-region-and-family> is <required> <quota-family> vCPUs in <region> (<remaining> remain)
PASS Anyscale on Azure prerequisites are ready
```

If you configured a managed GPU pool, the output also includes that pool's VM
SKU and its combined quota requirement. A final `PASS Anyscale on Azure
prerequisites are ready` line confirms that the full check passed.

If a check fails, follow the error and run `doctor` again. Install a missing
command, change an unavailable region or VM SKU in `.env`, or request more
capacity from [Azure Quotas](https://portal.azure.com/#view/Microsoft_Azure_Capacity/QuotaMenuBlade).
If the Anyscale CLI is missing, rerun `./scripts/anyscale-aks.sh bootstrap`. If
the CLI is not authenticated, run
`ANYSCALE_HOST=https://console.azure.anyscale.com .venv/bin/anyscale login`.

If an error is unfamiliar, ask GitHub Copilot Chat or another coding assistant
in Visual Studio Code to explain the failing check and identify the related
`.env` setting. Share the error text, but do not share credentials or tokens.
Verify every correction by running `doctor` again.
