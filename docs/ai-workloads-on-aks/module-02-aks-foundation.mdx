In this setup, you will deploy a public AKS cluster in **Region A**, along with
Azure Blob Storage, Azure Container Registry, Log Analytics, and a Flex VM in a
peered VNet in **Region B**. One Terraform apply creates both compute locations
and the Azure resources they need before the Flex VM joins AKS.

## What You Will Do

You will deploy the public AKS cluster, Flex VM, storage, registry, observability,
and network peering that the rest of the lab needs. After the apply, you will get
a kubeconfig, check that the cluster is healthy, and confirm both VNets are
peered before the Flex VM joins AKS.

## Architecture overview

```text
Region A (AKS home region)             Region B (Flex host region)
─────────────────────────────────      ───────────────────────────
  AKS cluster: aks-...-<region-a-short>  VNet: vnet-...-<region-b-short>
  VNet: vnet-...-<region-a-short>        Flex VM: vm-flex-...-<region-b-short>
  Storage, ACR, Log Analytics            (the VM joins AKS in Module 3)
  ↕ VNet peering ↔──────────────────────↕
```

Terraform creates both sides of the VNet peering before it creates the Flex VM,
so the host has a cross-region network path when you join it to AKS. It also
checks the live AKS network profile and waits for Cilium to become ready before
it starts the Flex VM.

Terraform creates AKS with no built-in CNI, then installs upstream Cilium with
cluster-pool IPAM, a VXLAN tunnel, and kube-proxy replacement. Cilium on the AKS
and Flex nodes allocates pod addresses from `TF_VAR_cilium_pod_cidr`, giving pods
in both regions one cluster-wide address space.

## Step 1: Review your deployment settings

The home region, Flex region, sizing, and Anyscale setting are already in `.env`.
Keep Anyscale disabled while Terraform builds the AKS foundation. Confirm:

```bash
grep -E 'azure_location|region_short|flex_region|anyscale_enabled' .env
```

Expected plan shape:

```text
TF_VAR_azure_location="<region-a-azure-name>"
TF_VAR_region_short="<region-a-short>"
TF_VAR_flex_region="<region-b-azure-name>"
TF_VAR_flex_region_short="<region-b-short>"
TF_VAR_anyscale_enabled="false"
```

:::info Using a fallback region
If AKS capacity in Region A is unavailable, choose another Anyscale-supported AKS
location, set `TF_VAR_azure_location` and `TF_VAR_region_short` in a separate env file, and run with
`ANYSCALE_AKS_ENV_FILE=.env.my-fallback ./scripts/anyscale-aks.sh apply`.
Region B stays a separate reachable location and must be rechecked for CPU quota.
:::

## Step 2: Preview the Azure resources

```bash
./scripts/anyscale-aks.sh plan
```

Example output:

```text
Terraform will perform the following actions:
  # module.aks.azurerm_kubernetes_cluster.this will be created
  # module.network.azurerm_virtual_network.this will be created
  # azurerm_virtual_network.flex will be created

Plan: <resource-count> to add, 0 to change, 0 to destroy.
```

This command prepares the Terraform values, checks the configuration, and creates
a plan file. Review the output before continuing. Resource totals can change
between versions. On a clean deployment, every planned action must be a create
and the summary must show `0 to change, 0 to destroy`.

## Step 3: Create the AKS foundation

```bash
./scripts/anyscale-aks.sh apply
```

Expected duration: **15-25 minutes** (AKS cluster creation is the longest step).
Terraform prints resource progress while Azure creates the cluster. Wait for the
apply to finish, then use the node, Cilium, and VNet peering checks below as the
evidence that the foundation is ready.

When complete, Terraform prints the AKS and network details you will use in the
next module:

```text
Outputs:
  aks_cluster_name = "aks-flexany-dev-<region-a-short>"
  aks_api_server_fqdn = "aks-flexany-dev-<region-a-short>-xxxxx.hcp.<region-a>.azmk8s.io"
  flex_vnet_id = "/subscriptions/.../vnet-flexany-dev-<region-b-short>"
  flex_host_vm_name = "vm-flex-flexany-dev-<region-b-short>"
```

:::caution Before you connect the Flex node
Continue only after AKS is running and both VNet peerings report `Connected` and
`Succeeded`. The Flex host needs that network path before it can join the cluster.
:::

## Step 4: Connect kubectl to the cluster

```bash
source .env
RG="rg-${TF_VAR_project}-${TF_VAR_environment}-${TF_VAR_region_short}"
CLUSTER="aks-${TF_VAR_project}-${TF_VAR_environment}-${TF_VAR_region_short}"

az aks get-credentials \
  --resource-group "$RG" \
  --name "$CLUSTER" \
  --overwrite-existing
```

Example output:

```text
Merged "aks-flexany-dev-<region-a-short>" as current context in /Users/operator/.kube/config
```

## Step 5: Check cluster health

```bash
kubectl get nodes -o wide
kubectl get pods -n kube-system
```

Expected output:

```text
NAME                                STATUS   ROLES   AGE   VERSION   INTERNAL-IP
<system-node-name>                  Ready    agent   <age> <version> <private-ip>
<cpu-node-name>                     Ready    agent   <age> <version> <private-ip>

NAME                                  READY   STATUS    RESTARTS   AGE
coredns-6d8f9d9b9f-abcde              1/1     Running   0          10m
konnectivity-agent-7c6d8dbf9f-fghij   1/1     Running   0          10m
kube-proxy-abcde                      1/1     Running   0          10m
```

You should see one `sys` node and one `cpu` node in `Ready` state. The CPU pool
starts with `min_count=1` and can scale to four nodes. The default CPU profile
does not create an AKS GPU pool. AKS can run additional system pods that are not
shown in the example. For every listed pod, check that `STATUS` is `Running` and
that `READY` shows all expected containers ready.

## Step 6: Verify the Cilium foundation

Terraform waits for the Cilium agent and Envoy DaemonSets to become ready on the
AKS nodes before the apply completes. Check the live network profile and Cilium
release before you provision the Flex host. The three commands are independent
views of the same foundation:

1. The AKS network profile proves that no built-in CNI owns pod networking and
  shows the pod and service CIDRs.
2. The Helm values prove that Cilium uses cluster-pool IPAM, VXLAN, and kube-proxy
  replacement.
3. The pod list proves that the Cilium agent and Envoy are running on the AKS
  nodes.

```bash
source .env
RG="rg-${TF_VAR_project}-${TF_VAR_environment}-${TF_VAR_region_short}"
CLUSTER="aks-${TF_VAR_project}-${TF_VAR_environment}-${TF_VAR_region_short}"

az aks show \
  --resource-group "$RG" \
  --name "$CLUSTER" \
  --query 'networkProfile.{plugin:networkPlugin,podCidr:podCidr,serviceCidr:serviceCidr}' \
  -o json

helm -n kube-system get values cilium -o json
kubectl -n kube-system get pods -l 'k8s-app in (cilium,cilium-envoy)' -o wide
```

Expected network profile:

```json
{
  "plugin": "none",
  "podCidr": "10.83.0.0/16",
  "serviceCidr": "10.100.0.0/16"
}
```

The Cilium values include `cluster-pool`, `tunnel`, `vxlan`, and
`kubeProxyReplacement: true`. They follow the upstream AKS Flex Node Cilium
sample. The final pod list must show the Cilium and Cilium Envoy pods in
`Running` state on each current AKS node. Keep all three command outputs; together
they record the CNI configuration and current agents that the Flex node will use
when it joins.

## Step 7: Verify the cross-region network connection

```bash
source .env
RG="rg-${TF_VAR_project}-${TF_VAR_environment}-${TF_VAR_region_short}"
AKS_VNET="vnet-${TF_VAR_project}-${TF_VAR_environment}-${TF_VAR_region_short}"
FLEX_VNET="vnet-${TF_VAR_project}-${TF_VAR_environment}-${TF_VAR_flex_region_short}"

az network vnet peering list \
  --resource-group "$RG" \
  --vnet-name "$AKS_VNET" \
  -o table

az network vnet peering list \
  --resource-group "$RG" \
  --vnet-name "$FLEX_VNET" \
  -o table
```

Expected fields:

```text
Name         ResourceGroup          PeeringState    ProvisioningState
-----------  ---------------------  --------------  -------------------
aks-to-flex  <resource-group>       Connected       Succeeded
flex-to-aks  <resource-group>       Connected       Succeeded
```

Terraform creates both directions. Both `aks-to-flex` and `flex-to-aks` must show
`PeeringState=Connected` and `ProvisioningState=Succeeded`. Do not continue while
either direction is disconnected, failed, or still provisioning. This confirms
the network path before the Flex VM joins AKS.

## Success evidence

You can move on when the `sys` node pool is `Ready`, Cilium and Cilium Envoy are
running, and both VNet peerings show `Succeeded`. Keep the network profile,
Cilium values, and peering output. Together, they show that AKS has no built-in
CNI, Cilium is ready, and the cross-region network path is live before the Flex
host joins.
